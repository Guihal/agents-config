# UI-kit contract — компонентная модель «как в вёрстке»

Приоритет правил: где этот файл противоречит harness-lib `design-standard.md` /
`figma-console-workflow.md`, управляют файлы figma-design.

Компонентная модель в Figma повторяет структуру кода (requirements §2):
дизайн-токены + UI-компоненты везде, единая шкала отступов, готовый кит
секций/контейнеров/элементов, каждый текст — элемент кита со своими отступами.
Носитель — нативный механизм Figma: COMPONENT / COMPONENT_SET / variants /
component properties / INSTANCE (доступность подтверждена live-пробой MCP;
инвентаризация — `findAllWithCriteria({types:["COMPONENT","COMPONENT_SET",
"INSTANCE"]})`, см. `mcp-workflow.md` §3).

## 1. Слои кита и порядок сборки

Зависимости направлены только вниз (потребитель знает поставщика, никогда
наоборот):

```text
Tokens (variables + styles, tokens-contract)
  → _base-примитивы
  → текст-кит (типографические роли)
  → компоненты (variants + component properties)
  → секции/контейнеры как компоненты
  → экраны (только instances)
```

Порядок сборки в UI-kit pass — снизу вверх: `_base`-примитивы и текст-кит,
затем компоненты, затем секции/контейнеры. Экран никогда не является
источником кита: ретроспективное «выделение кита из готовых экранов» —
hard failure, экраны — только потребители.

Двухрежимный старт (из скелета, обязателен): если кит в файле уже есть —
researcher инвентаризует его, worker нормализует/расширяет; параллельный
дубликат (`Button 2`) рядом с существующей системой запрещён. Если кита нет
или он номинальный — worker собирает минимальный реальный кит ДО любого
экрана.

## 2. `_base`-примитивы

- Атомарные контролы: Button, Input, Select, Checkbox, Radio, Chip, Icon
  slot, Avatar и т.п. — по реальной потребности текущего скоупа.
- Внутри примитива: авто-лейаут, значения layout (padding/gap/min-max) —
  биндинг к spacing-переменным шкалы; цвета/типографика — к переменным/стилям
  (tokens-contract).
- Именование семантическое (`Button/Primary`, не `Frame 42`); непонятным
  контролам — description с контрактом состояний.

## 3. Текст-кит (типографические роли)

- Роли: **display / heading / body / caption / label** (или конвенция
  проекта). Роль — компонент (`text/display`, `text/heading`, …), содержащий
  TEXT-узел с биндингом fontSize/lineHeight/fontFamily к переменным и
  **собственными отступами роли** (padding роли — часть компонента, не
  ручные поля вокруг текста на экране).
- Варианты ролей — только реальные оси (`Size=sm|md|lg`, `Weight=regular|…`);
  не плодить кросс-произведение под каждый контентный случай. Контент строки
  задаётся TEXT component property (`Text`/`Content`) у инстанса, а не
  комбинаторикой компонентов.
- SPEC назначает роли контенту экрана («этот блок — heading/md, этот —
  body/lg»); worker не изобретает роли мимо SPEC.
- **Текст в экранах — только инстанс роли текст-кита.** Сырой TEXT-узел в
  экранном фрейме мимо кита — finding `bare-text` (гейт `bare-text scan`,
  `geometry-gates.md`). Тексты внутри компонентов кита — часть анатомии
  компонента.

## 4. Компоненты: variants и component properties

- **Variants — реальные оси** (независимые): `State=default|hover|disabled`,
  `Size=sm|md|lg`, `Tone=primary|secondary`. Запрещены «упакованные» значения
  (`Style=PrimaryLargeDisabled`) и мега-компоненты, чьё кросс-произведение
  кодирует несвязанные лэйауты.
- **Component properties** — по назначению:
  - `TEXT` — контент строки/лейбла;
  - `BOOLEAN` — включаемый слот/элемент (иконка, счётчик бейджа);
  - `INSTANCE_SWAP` — сменный слот (иконка внутри кнопки).
- Скрытие через `visible`-биндинг BOOLEAN-переменной — там, где состояние
  переиспользуется (tokens-contract §2); статическое скрытие состояний в
  кит-компонентах — не замена вариантам.
- У каждого компонента: семантическое имя, description для неочевидных
  состояний/accessibility-контракта.

## 5. Секции/контейнеры как компоненты

- Повторяющиеся композиции — компоненты кита: Card, List item, Form section,
  Page header, Toolbar, Empty state, навигационные блоки, layout-контейнеры
  (shell-обёртки с контентной шириной из `size/container` modes).
- Частичные композиции НЕ несут продуктовых данных: блок с реальным контентом
  конкретного экрана — это скрытый экран, а не кит-компонент (blocker).
- Ширины контейнеров — биндинг minWidth/maxWidth к `size/container` (значения
  по режимам Desktop/Mobile, tokens-contract) — один кит кормит оба
  разрешения.
- Вёрстка всего кита и экранов — сразу в auto-layout (направление, gap,
  padding, alignment, fill/hug, wrap). Абсолютное позиционирование —
  исключение (оверлеи/декор), каждый случай явный.

## 6. Зона кита на канве

- Кит живёт в **своей именованной секции** (`UI Kit` / конвенция файла),
  отдельной от продуктовых секций и reference-зон; в MANIFEST —
  `canvasRegions.uiKit` (protected: true).
- Гуттеры между семантическими областями канвы ≥ 200px; sibling-фреймы кита
  не пересекаются.
- Конвенция расширения канвы — **right-to-left**: новые крупные группы
  добавляются левее существующего вывода (не про RTL-текст продукта).
- Новая группа/фрейм не пересекает существующие топ-левел узлы: перед
  размещением — probe детей страницы и выбор свободного места.

## 7. Потребители: «у foundation есть консюмер в текущем скоупе»

- Каждый добавленный foundation-элемент (примитив, роль текст-кита, компонент,
  секция, переменная, стиль) имеет **минимум одного потребителя в текущем
  скоупе** (SPEC/экраны). Спекулятивная космонавтика — overdesign, blocker:
  формально существующий компонент с 0 потребителями = blocker.
- Минимальность не значит скудость: кит должен покрывать реально используемые
  семантики экранов (непокрытая семантика = `missing-design-system`-класс
  дефектов из скелета).

## 8. Экраны — только из instances

- Экранные фреймы собираются **только из instances кита** + текстовых
  инстансов ролей; повторные контролы «вручную» (копия анатомии компонента с
  type ≠ INSTANCE) — finding `detached-copy`.
- Все layout-числа на экранах — биндинг к переменным (spacing/размеры) и
  переменные/стили (цвета/типографика); голые значения мимо токенов —
  `off-token-value`, значения мимо шкалы — `spacing-scale-violation`
  (гейты в `geometry-gates.md`).
- Каждый экран существует в двух разрешениях (desktop + mobile фрейм), оба
  собираются из одного и того же кита; метрики ширин приходят из modes тех же
  переменных. Отсутствие/неправильная геометрия одного из фреймов —
  `viewport-missing` (гейт `viewport-check`).
- Раскладка экрана на канве: именованная секция фичи/флоу, sibling-фреймы
  (desktop, mobile, состояния) рядом, RTL-конвенция, гуттеры ≥ 200px.

## 9. Границы против вёрстки в коде

Паритет с вёрсткой — структурный (токены, шкала, кит, роли, instances), не
буквальный: имена компонентов/переменных следуют конвенциям проекта, а
одноразовые декоративные исключения остаются локальными, только если они
явно объявлены в SPEC. Молчаливых исключений нет: каждый сырой литерал,
каждая копия мимо инстанса, каждый текст мимо роли — finding на гейте.
