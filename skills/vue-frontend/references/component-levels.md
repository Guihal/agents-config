# Component Levels — L0–L4, сплиты, границы логики

Адаптация Clean Components Toolkit (М. Тиссен) и Core-Adapter (toss.tech).
Всё ниже — дефолты; проектные правила (CLAUDE.md/AGENTS.md репо) сильнее.

## Уровни

| уровень | роль | права и запреты | бюджет строк |
|---|---|---|---|
| L0 Page | точка входа роута | собирает фичи, читает store read-only | <100 |
| L1 Feature | оркестратор фичи | владеет `provide()`, store full CRUD | <200 |
| L2 Controller | связывает фичу с UI | store через inject, управляет секциями | <150 |
| L3 Humble | чистая презентация | только props + emit; store и composables запрещены | <100 |
| L4 Atomic | дизайн-примитив | без детей; анатомия — в `ui-standards` | <50 |

Аннотация `<!-- @level L2-Controller -->` — опциональная конвенция: уровень
компонента виден на ревью без чтения кода.

Анатомия, варианты, состояния и a11y-минимум элементов уровня L4 —
`/home/penis/.agents/skills/ui-standards/SKILL.md` (не повторять их здесь).

Дерево назначения уровня:

- Компонент — точка входа роута? → **L0**
- Инкапсулирует сценарий фичи и владеет provide-контрактами? → **L1**
- Оркестрирует часть фичи, без своего provide? → **L2**
- Показывает данные, которые дали, и эмитит события? → **L3**
- Единый UI-примитив без детей? → **L4**

## Пороги сплита (дефолты)

- **Больше ~200 строк — делить; 150+ — ревизия на сплит.** Бюджеты уровней —
  мягкие ориентиры, не закон.
- **3+ ветки v-if «режимов»** → extract conditional: каждая ветка — отдельный
  Humble-компонент, родитель только выбирает.
- **Тело v-for длиннее ~20 строк** → item-компонент.
- **2–3 секции по 50+ строк** → скрытые подкомпоненты: оркестрация остаётся
  у родителя, разметка уходит вниз.
- **2+ независимых источника данных** → composable на каждый.
- **Одна и та же логика в 3+ компонентах** → composable или shared utility.

## Когда НЕ делить

- Статичная разметка 100–150 строк с минимумом логики.
- Сплит добавляет файлы, но не понятность.
- Простой parent-child с ≤3 props.
- Паттерн встречается один раз — извлекать, когда появился второй.

## API компонента

- `defineProps<{ ... }>()` — типовой; `const props =` — только если props
  реально используются в script; деструктуризация — только ради дефолтов.
  Runtime-валидация (`PropType`, `required`) при TS не нужна.
- `defineEmits<{ submit: [data: FormData]; cancel: [] }>()` — события с
  типизированными payload'ами и семантичными именами. camelCase в script,
  kebab-case в шаблонах — как в проекте, единообразно.
- `defineModel<T>()` — для любого v-model, включая именованные модели;
  не собирать вручную `modelValue` + `update:modelValue`.
- Слоты — через `#name` и явный `<template>` (включая `#default` — дефолт,
  вопрос вкуса в команде).
- **Preserve Whole Object:** 3+ связанных props одной сущности → один
  объект-состояние.

Счётчик props (дефолты): 1–4 — ок; 5+ или
3+ handler-пропса — сигнал: собрать связанные в объект-состояние (Preserve
Whole Object), уйти в provide/inject (`references/provide-inject.md`) или
сплит.

## Границы извлечения логики

### Core-Adapter

- **Core — чистый TS:** без `ref`/`reactive`/`computed`/`watch`/`onMounted`/
  `inject`/`provide` и любых импортов из `vue`; чистые функции input→output,
  классы, типы, константы.
- **Adapter — тонкий composable, 5–30 строк:** оборачивает core в
  `ref`/`computed`, подключает lifecycle. UI-сайд-эффекты (toast, alert) —
  не здесь: их делает компонент поверх adapter, реагируя на его
  error/loading state (закон 5 SKILL.md).
- Core живёт там, где: чистой логики 10+ строк; тот же расчёт нужен в 2+
  composables; нужна проверка без компонентного контекста (composable с
  lifecycle/inject требует компонентного контекста — ещё одна причина
  держать ядро чистым).

### Composables

- Порог извлечения: 1 использование → inline на месте; 2 реальных →
  кандидат; 3+ → извлекать. Никогда не извлекать заранее.
- `use`-префикс — только если composable использует lifecycle API; иначе это
  plain function.
- Один composable — одна забота; связанные `ref` + `watch` + lifecycle —
  вместе; каждый ресурс чистится в `onUnmounted`.
- Состояние — per-call: `reactive` на уровне модуля шарится между всеми
  вызовами (исключение — синглтоны-сторы вроде Pinia).
- Без UI-логики: toast/alert — в компонент; composable возвращает error state.
- 4+ параметра → options-объект; ≤3 — позиционные. Возврат — именованный
  объект, не массив.

### Чьё это состояние?

- Персистится или нужно 2+ фичам → store (механика Pinia — вне скилла).
- Исчезает при unmount → локальный `ref`.
- Координация внутри поддерева фичи → provide/inject.
- Чистый расчёт → util / core.

## Файловая организация (дефолт)

`features/<feature>/` → `core/`, `composables/`, `components/{ui,sections}/`,
`store/`, `types.ts`, `constants.ts`. Проектная структура сильнее.
